## Problem

The user was engaged in a multi-workstream effort to convert a Figma design—the “TASL Canteen Software” file (roughly 10–11 screens, file ID `XEXcrSYyHhKXVLDLbRVnJg`)—into a functional application, while simultaneously exploring a data backend for canteen billing (employee, order, and payment records). The work was not a single linear task but a set of interleaved technical and product problems:

1. **Data/API layer.** The user needed to relate Airtable employee, order, and payment records, retrieve employee-specific records through an API, and find a free SQL database with an API-hosting path. A central ambiguity was whether relationships should be handled by Airtable’s linked-record model, direct API filtering (`FILTER_BY_FORMULA`), or a separate hosted SQL backend.

2. **Frontend tooling on Windows.** The user wanted to turn Figma UI designs into deployable application code without relying on paid export features. Constraints included Windows/PowerShell/VS Code, free tooling only, and a target that evolved from web/PWA considerations toward React Native. The environment initially lacked or failed to recognize Node.js/npm, Git, and the correct working directory.

3. **Monorepo and codegen.** The user selected the `kat-tax/figma-to-react-native` repository, which turned out to be a seven-project pnpm monorepo rather than a standalone npm CLI. The goal was to fetch a Figma file via REST API, save the JSON, transform it into responsive React Native components, and run the app on Android.

4. **Android native build.** During `app:buildCMakeDebug[arm64-v8a]`, the linker (`ld.lld`) could not resolve fundamental C++ standard library symbols (`std::__ndk1::basic_string`, `operator new/delete`, `__cxa_*` exception-handling symbols, RTTI vtables, `__gxx_personality_v0`). The build used NDK r27.1.12297006 and React Native’s `OnLoad.cpp` (TurboModule registration) on a Windows host. The emulator also failed to launch.

5. **Renderer and PWA pivot.** The generated project contained a large Figma-derived JSON file, a JSX renderer, `service-worker.js`, `index.css`, and `app.jsx`. The renderer encountered nested undefined-property errors (`data.layers`, `layers`, `frame`, `absoluteBoundingBox`). The user eventually recognized that the project was browser-targeted rather than native React Native, because `App.jsx` imported `SafeAreaView`, `StatusBar`, and `StyleSheet`—incompatible with a browser runtime.

## Approach

The user’s reasoning moved from broad tool evaluation to increasingly concrete, error-driven debugging across the workstreams.

### Data and API exploration
The user first compared three ways to relate Airtable data: `FILTER_BY_FORMULA` in API requests, linked records plus Lookup/Rollup fields, and filtered views for manual inspection. The conversation then shifted toward a standalone SQL-backed service, comparing Supabase (PostgreSQL with an auto-generated REST API), Railway or Render (custom backend requiring a separately deployed service), and db4free (database-only MySQL). SQL behavior was investigated progressively through concrete errors rather than as a single configuration task: unquoted table names containing spaces caused PostgreSQL syntax errors; a missing required `Payment Amount` exposed a `NOT NULL` constraint; multi-column `ALTER COLUMN` behavior exposed PostgreSQL/MySQL syntax differences. The user then explored bulk inserts, random test records, deletion by employee ID, and signup storage.

### Windows environment and Figma-to-React Native setup
The user assessed paid/no-code tools (Bravo Studio, Locofy, Anima, TeleportHQ, Penpot, manual conversion) and rejected paid code-export because Bravo Studio’s free tier did not provide the desired code export or PWA publishing. After selecting `kat-tax/figma-to-react-native`, the user worked from source-control setup to monorepo configuration: installed Node/npm and Git, cloned the repository, created a `.env` file with a Figma PAT, inspected `package.json`, recognized the pnpm workspace scripts, and ran `pnpm install`. The user consistently supplied exact terminal errors, enabling diagnosis based on the actual environment rather than generic instructions.

### Monorepo repair and Figma API integration
The user diagnosed a broken workspace: `pnpm-workspace.yaml` was missing, the `figma-to-react-native` package folder was missing, and the root `package.json` had no `workspaces` field. The repair involved creating `pnpm-workspace.yaml` with `packages: ["packages/*"]`, adding `workspaces` to the root `package.json`, and initializing the missing package with `pnpm init`. PowerShell `@` splatting required quoted `--filter` arguments; when that failed, the user used `-w` (workspace root) and then `cd` into the package directory for direct `pnpm add`.

For the Figma API script, the user wrote `import-figma.js` using Node 22’s native `fetch`, fixed ES module syntax (`import fs from 'fs'`, added `"type": "module"`), and removed `node-fetch` to avoid ESM/CommonJS friction. After verifying the token and file ID, the script successfully authenticated and saved `figma-design.json`.

For component generation, the user designed `Screen1.js` to map `TEXT`, `IMAGE`, and `BUTTON` layers from `figma-design.json` to React Native primitives, using `Dimensions` for responsive scaling against a 375×812 baseline.

For Android, the user installed JDK 17 (selected over 21 for React Native/Android Gradle Plugin LTS support), set `JAVA_HOME` and `PATH`, installed Android Studio/SDK, created an AVD via the Device Manager GUI, fixed `ANDROID_HOME`/`ANDROID_SDK_ROOT`, and added `platform-tools`, `emulator`, and `cmdline-tools` to `PATH`. Gradle memory was tuned downward: `org.gradle.jvmargs=-Xmx1024m` and `kotlin.daemon.jvmargs=-Xmx1024m`, because the machine could not reserve a 2 GB contiguous heap.

### Android C++ linker failure
The user presented the complete linker error output in chunks. No independent diagnosis or fix was shown in the record; the user was sharing error information for external help. The error pattern indicated a C++ runtime linkage issue, but the user had not yet isolated or tested a hypothesis.

### Renderer debugging and PWA pivot
The user supplied four related runtime errors and asked for a connected root-cause analysis rather than treating them as independent bugs. The user temporarily moved into Figma to verify frame dimensions (1920×1080), hyperlinks, and text strokes, reasoning that a malformed design hierarchy would continue producing layout and undefined-property failures even if downstream code guards merely hid the crashes. The user inspected the renderer’s image-scaling code and corrected the assistant when the assistant misunderstood file identity: `screen1` was a Figma tab name, not the React Native file or JSON payload.

The user then asked for an explicit explanation of the project artifacts—the large JSON, JSX renderer, service worker, CSS, and app entry file—showing deliberate system discovery. The user identified the source repository and requested an import script that fetches only one Figma screen using the `/nodes?ids=1-2` endpoint rather than the whole-file endpoint. A later implementation still saved the full API response envelope under `screen1.json`, so the intended isolation was not guaranteed.

Finally, the user reassessed the runtime target: because `App.jsx` used React Native primitives and lacked a browser bootstrap, the user chose React DOM/PWA over direct React Native rendering. This meant replacing `SafeAreaView`, `StatusBar`, and `StyleSheet` with DOM/CSS, mounting into `<div id="root">`, and adding `src/index.js`, `public/index.html`, and `public/manifest.json`. The user attempted `npm start`, but npm was not recognized; troubleshooting narrowed the cause to Node not being installed, missing PATH configuration, or a stale terminal environment.

## Decisions

**Data layer.** Supabase was identified as the lowest-code backend because it combines PostgreSQL with an auto-generated REST API. Railway and Render were recognized as better for a custom API but requiring more operational work. Airtable linked records were preferred when Airtable itself needed to maintain employee–order–payment relationships. API filtering was distinguished from relational modeling: `FILTER_BY_FORMULA` suited dynamic retrieval, while Lookup/Rollup fields suited dependency-free aggregation. Passwords were not to be stored in plaintext; the proposed signup schema used `password_hash` with bcrypt/Werkzeug-style hashing and a unique email constraint. Database constraints were treated as business rules: supply the required value, permit `NULL`, or define a default. Bulk row insertion was preferred over repeated inserts, including a possible `INSERT ... SELECT` workflow for importing employee IDs.

**Frontend tooling.** Paid code-export tools were rejected in favor of a free workflow. Bravo Studio was insufficient because its free tier lacked code export and PWA publishing. React/Next.js was selected as the more scalable choice for authentication, APIs, state, and dashboard-like interfaces; plain HTML/CSS/JS remained the lightweight alternative. The `kat-tax/figma-to-react-native` repository became the selected implementation path. The user adopted a pnpm-based setup after inspecting `package.json`, rather than continuing with earlier `npx` assumptions. The Figma PAT was intended to remain in a project-root `.env` file.

**Monorepo and Android.** A pnpm monorepo with `packages/*` was chosen to keep `figma-ui`, `figma-build`, and app code co-located. `"type": "module"` was added because Node 22 defaults to ES modules. Native `fetch` was chosen over `node-fetch` to remove an extra dependency and ESM/CommonJS friction. JDK 17 was selected over 21. Gradle heap was reduced to 1 GB rather than increased, because the machine could not reserve 2 GB contiguous heap. The Kotlin daemon was also capped at 1 GB. An AVD was created via Android Studio’s GUI to ensure correct system image and hardware profile.

**Android C++.** The user explored (but did not verify) downgrading NDK 27 to 25/26 for fbjni compatibility, setting `ANDROID_STL=c++_shared`, enabling C++17 with `-D_GLIBCXX_USE_CXX11_ABI=1`, and adding `-frtti -fexceptions`.

**Renderer and PWA.** The four undefined-property errors were treated as one dependency chain: missing `data` → missing/unassigned `layers` → missing layer `frame` → missing `absoluteBoundingBox`. The user prioritized fixing the upstream Figma structure before accumulating runtime guards. Responsive scaling was implemented via `width / 375` and `height / 812`. Raw design data was separated from executable behavior. The Figma API import was scoped to node `1-2` to reduce payload. The architecture was moved from React Native to React DOM/PWA for browser execution, with standard browser mounting files created.

```sql
ALTER TABLE "Canteen_Bill_Management"
```
