# Office Canteen Order & Bill Management System: A Parallel Exploration of Code and No-Code Approaches

## Problem Framing and Initial Ambiguity

The project began with a clear but open-ended need: build an internal tool to manage office canteen orders and bills. The system had to track employees (users), their orders and bills, payments received, and outstanding balances. What made this a genuine 0→1 challenge was the complete absence of a predetermined tech stack. The user faced fundamental ambiguities across every layer: whether to write custom code (Flask/SQLAlchemy) or adopt a no-code platform; how to model relational data—users linked to orders linked to payments linked to outstanding amounts—in a tool like Airtable; how to authenticate against the Airtable API now that API keys were deprecated in favor of Personal Access Tokens (PATs); how to fetch only the fields needed, handle pagination, and filter records by the currently logged-in user; which frontend tool would pair best with Airtable (Thunkable, Bravo Studio, FlutterFlow, Glide, Bubble, Retool, AppGyver, Adalo, Framer); and what mobile or PWA deployment options existed within a free-tier budget. The user started with a blank slate, learning both SQL-backed development and the no-code paradigm simultaneously.

## Parallel Exploration Strategy

Rather than committing to a single path, the user ran four investigation tracks in parallel from mid-December 2024 through mid-February 2025.

**Track 1: Code-First Prototype (Flask + SQLAlchemy).** On December 12, the user built a working Flask backend (`app.py`) with SQLAlchemy models—`User(id, name, contact_info)` and `Order(id, user_id, amount, status)`—backed by SQLite (`orders.db`). REST endpoints covered the full CRUD cycle: `POST /users`, `POST /orders`, `GET /users/<id>/orders`, and `PATCH /orders/<id>/pay`. The flow was verified end-to-end via Postman and curl. This gave the user a concrete mental model of the data relationships and API surface before exploring no-code alternatives.

**Track 2: No-Code Backend (Airtable).** Starting December 19, the user designed an Airtable base named "Office Canteen Order and Bill Management" with four tables: `Customers` (Employee ID, Name), `Orders` (linked to Customer, amount, status), `Payments` (linked to Customer, amount, date), and `Outstanding Amount` (rollup/summary). Linked records established the relationships; rollup fields and formulas computed balances automatically. The user also built screens in Airtable's Interface Designer—a calculator-like view with a customer dropdown, number input for amount, "Add Bill" button, and balance display—demonstrating that Airtable could serve as both backend and a limited internal UI.

**Track 3: No-Code Frontend Evaluation.** The user tested a succession of frontend platforms against concrete criteria: screen limits, PWA support, Figma import capability, API integration ease, publishing cost, and learning curve. Retool was tried but abandoned due to drag-and-drop friction. Thunkable allowed free publishing and a Web API component for Airtable integration, but the user hit limitations duplicating buttons for a calculator grid, configuring a drawer navigator, and handling multi-select components. Bravo Studio offered direct Figma import and a free tester (Bravo Vision), but publishing required a paid plan. FlutterFlow supported Figma asset export (PNG/SVG), a free tier, PWA publishing, and multiple backend options (Firebase, Supabase, Airtable), though the Figma-to-Flutter plugin workflow was noted as an alternative to manual recreation. Glide, Bubble, AppGyver, Adalo, and Framer were assessed as fallbacks; AppGyver was noted as "truly unlimited free" but with a steep learning curve.

**Track 4: Airtable API Deep-Dive.** This became the most technically intensive track. The user learned the Airtable REST API from first principles: extracting the Base ID (`applNfL1uzUK6w1P1`) from the API documentation, browser URL, or Developer Hub; distinguishing table IDs (`tbl...`, `tble...`) from names; using field IDs (`fld...`) rather than names for stability; constructing requests with the `fields[]` parameter (URL-encoded as `fields%5B%5D`) to reduce payload; applying `filterByFormula` for server-side filtering (e.g., `{Employee ID}='emp123'`); handling pagination via the `offset` parameter with `maxRecords=100`; and authenticating with a PAT (`Authorization: Bearer pat...`) using minimal scopes (`data.records:read`, `data.records:write`, `schema.bases:read`). Every error—401 Unauthorized, `INVALID_PERMISSIONS_OR_MODEL_NOT_FOUND`, single-record responses—was treated as a signal to refine the mental model.

## Key Decisions and Trade-Offs

The parallel tracks converged on a set of deliberate decisions, each documented with its rationale.

| Decision | Rationale / Trade-off |
|---|---|
| **Airtable as primary backend** over Flask/MySQL | Faster MVP; built-in UI via Interface Designer; no hosting or database maintenance; relational features (linked records, rollups) sufficient for an internal tool; accepted scalability ceiling. |
| **Personal Access Tokens** over deprecated API keys | Security and future-proofing; selected minimal scopes to follow least-privilege principle. |
| **Field IDs (`fld...`)** over field names in API requests | Field names can change; IDs are immutable, preventing silent breakage. |
| **`filterByFormula`** for user-scoped data | Server-side filtering reduces payload and client-side logic; pattern `{fldIYmxrGYcyDTezd}="emp123"` used for payment history. |
| **Pagination via `offset` + `maxRecords=100`** | Airtable enforces a 100-record hard limit per request; iterative fetch loop required. |
| **Thunkable for mobile frontend (initially)** | Free publishing, drag-and-drop, Web API component for Airtable; later limited by multi-select and button-duplication friction. |
| **Bravo Studio for Figma→App** | Direct Figma import; abandoned when publishing proved paid-only. |
| **FlutterFlow as alternative** | Figma asset import, free tier, PWA support, flexible backend options. |
| **Glide/AppGyver/Bubble as fallbacks** | Evaluated for PWA, screen limits, learning curve; kept as options if primary paths blocked. |

**Architecture decisions** solidified around a clear data model: `Customers` (Employee ID `fldkLwpg2c1Y7zj6M`, Employee Name `fld5wVhJydCuycgZn`) → `Orders` (linked to Customer, amount, status) → `Payments` (linked to Customer via `fldIYmxrGYcyDTezd`, Payment Amount `fldFwFPoP4kHM8Umi`, Payment Date `fld4Omrlr0Qq2p6M`) → `Outstanding Amount` (rollup/formula summary). The canonical API request pattern became:

```
GET /v0/{baseId}/{tableId}?fields[]=fldX&fields[]=fldY&filterByFormula=...&maxRecords=100&offset=...
Authorization: Bearer pat...
```

## Build, Iteration, and Debugging Episodes

The implementation phase was defined by a series of concrete debugging cycles, each triggered by an API error and resolved through hypothesis testing.

**Flask Prototype (Dec 12).** The user created `app.py`, defined models, implemented endpoints, and verified CRUD via Postman. This established a working reference implementation and confirmed the data model logic.

**Airtable Base Configuration (Dec 19 – Feb 15).** The user created the four tables with precise field and table IDs:
- `Customers` (`tbl0iPhTGUEbKGt6y`)
- `Orders`
- `Payments` (`tble7CRyEW25W8bWM`)
- `Outstanding Amount` (`tbl4a3vsWLpMvzIN4`)

Linked records connected Customers to Orders and Payments. Rollup fields on `Outstanding Amount` aggregated payment totals; formula fields computed running balances. Interface Designer screens provided a no-code internal dashboard.

**API Integration Debugging (Jan 27 – Feb 15).** This period produced the richest technical evidence.

1. **401 Unauthorized.** Initial requests failed. The user generated a PAT in the Airtable Developer Hub, added the `Authorization: Bearer pat...` header, and verified the token worked in Postman.
2. **`INVALID_PERMISSIONS_OR_MODEL_NOT_FOUND`.** Switching from table name (`Payments`) to table ID (`tble7CRyEW25W8bWM`) resolved the error. The user also confirmed the PAT scopes included `data.records:read` for the specific base.
3. **Single Record Returned.** A request for payment history returned only one record. The user recognized Airtable's default page limit, added `maxRecords=100`, and implemented an `offset` loop to fetch all pages.
4. **Field Selection.** Early requests returned all fields, bloating payloads. The user adopted `fields[]=fldX` (URL-encoded `fields%5B%5D=fldX`) to request only `Payment Amount` and `Payment Date`.
5. **User-Scoped Filtering.** To show a logged-in employee only their payments, the user constructed `filterByFormula=({fldIYmxrGYcyDTezd}="emp123")`, leveraging the linked-record field ID in the Payments table.

**Frontend Experiments.** In Thunkable, the user built a calculator grid by duplicating buttons, added a drawer navigator, and connected the Web API component to the verified Airtable endpoints. In Bravo Studio, the user imported a Figma design, bound the same API endpoints, and tested in Bravo Vision (free), but could not publish without a subscription. In FlutterFlow, the user exported Figma assets as PNG/SVG, recreated the layout manually, and noted the Figma-to-Flutter plugin as a potential accelerator.

## Outcomes Achieved

By mid-February 2025, the user had produced a set of functional, verified artifacts:

- A working Flask/SQLite backend with full CRUD (`orders.db`).
- An Airtable base with four linked tables, rollups, formulas, and Interface Designer screens.
- Verified, reusable API request patterns:
  - Employee list: `GET /v0/applNfL1uzUK6w1P1/Customers?fields[]=fldkLwpg2c1Y7zj6M&fields[]=fld5wVhJydCuycgZn`
  - Payment history for a user: `GET /v0/applNfL1uzUK6w1P1/tble7CRyEW25W8bWM?fields[]=fldFwFPoP4kHM8Umi&fields[]=fld4Omrlr0Qq2p6M&filterByFormula=({fldIYmxrGYcyDTezd}="emp123")`
  - Outstanding amount detail: `GET /v0/applNfL1uzUK6w1P1/tbl4a3vsWLpMvzIN4/{recordId}`
- A documented pagination handling pattern (iterative `offset` fetch).
- A comparative evaluation matrix for eight-plus no-code platforms covering pricing, PWA support, Figma import, screen limits, and API integration ease.

**Not yet achieved:** an end-to-end deployed application (frontend + backend + auth) in any platform; user testing with actual canteen staff; payment gateway integration (Stripe was mentioned but not implemented); a published mobile app or hosted PWA; performance benchmarks or scale testing.

## FDE / APM Competency Evidence

The conversation demonstrates a clear pattern of competencies, each grounded in specific behaviors.

**Problem Solving — Strong.** The user systematically debugged every API error: 401 (regenerated PAT, checked scopes), `INVALID_PERMISSIONS` (switched table name→ID, verified permissions), single-record responses (identified pagination limit, implemented offset loop), field selection errors (learned field IDs vs. names, URL encoding). Each error led to a refined mental model and a corrected, reusable request pattern.

**Technical Judgment — Strong.** The user evaluated eight-plus platforms on concrete, weighted criteria (PWA, screen limits, Figma import, API integration, publishing cost, learning curve). The choice of Airtable for MVP was justified by speed, built-in UI, and sufficient relationality. The decision to use minimal PAT scopes and field IDs reflected security and stability awareness.

**Learning & Resourcefulness — Strong.** The user conducted a self-directed deep dive into the Airtable REST API: discovering Base ID extraction methods (docs, browser URL, Developer Hub), mastering `fields[]`, `filterByFormula`, `offset`, `maxRecords`, URL encoding (`%5B%5D`), and the PAT deprecation timeline. Patterns transferred across tools (Postman → Bravo → Thunkable → curl). The user built a complete mental model of Airtable's ID hierarchy (base `app...`, table `tbl...`/`tble...`, field `fld...`, record `rec...`, view `viw...`).

**Systems Thinking — Moderate.** The user designed a multi-table Airtable schema with linked records, rollups, and formulas. They understood pagination as a system constraint requiring an iterative fetch loop and recognized that Interface Designer is internal-only, necessitating a separate frontend for external users. Evidence of failure-propagation analysis or second-order effects at scale is limited.

**Product Judgment — Moderate.** The problem was framed as an internal canteen tool, prioritizing MVP speed over customization. Core entities (employee, order, payment, outstanding) were scoped. No-code was chosen to avoid hosting and backend maintenance. No evidence of user interviews, success metrics, or a formal prioritization framework (RICE, MoSCoW) appears in the conversation.

**0→1 Execution — Moderate.** A working Flask prototype with full CRUD was built. The Airtable base was configured with a relational schema, formulas, rollups, and Interface Designer screens. API integration patterns were implemented and tested. However, no deployed end-to-end flow with real users exists; frontend-backend integration was validated only in testing tools (Postman, Bravo Vision).

**Outcomes & Communication — Weak.** No documented success criteria, KPIs, or validation plan. No stakeholder communication artifacts. No technical decision log for handoff. The conversation remains exploratory Q&A rather than delivery-oriented.

**Important limitations:** No real-user or stakeholder involvement; no production deployment; no performance, security, or scale validation; frontend-backend integration tested only in isolation; payment processing, notifications, multi-user auth/authorization, monitoring, and CI/CD not implemented.
