# Evidence Extraction: TASL Canteen Application

## 1. Problem Statement & Goal

**Problem:** The TASL Canteen application required a consistent multi-screen React frontend (CreateBillScreen, Dashboard/Calculator, OrderHistoryScreen, PaymentsListScreen) with unified navigation, drawer behavior, branding, and card layouts. Multiple screens exhibited layout drift, inconsistent drawer positioning, prop-shadowing bugs, and TypeScript type conflicts that prevented proper rendering and navigation.

**Goal:** Establish a coherent, cross-screen UI standard where all screens share:
- Fixed-position Sheet/drawer trigger at top-left (`top: 12px, left: 12px`)
- Consistent header structure (logo + centered title + cart button)
- Standardized card components with spacing, shadows, and borders
- Uniform menu item ordering (first item = "Create a Bill")
- Centralized navigation logic across screens

**Ambiguities:**
- Screen-specific requirements varied (e.g., OrderHistoryScreen needed 3 bill cards with status badges; PaymentsListScreen needed a "All Payments" header card)
- Some inconsistencies remained between screens (e.g., menu item ordering differed between CreateBillScreen and OrderHistoryScreen)
- The application lacked persistent storage for bills (state-only, lost on refresh)

## 2. User Reasoning & Actions

The user progressively requested specific fixes and refinements across episodes:

- **Episode 1 (Baseline):** Provided reference screens (registration, login, dashboard/calculator) as immutable visual contracts. Decision: do not alter referenced designs without explicit authorization.
- **Episode 2 (CreateBillScreen/Dashboard Alignment):** Modified menu positioning (fixed at top-left) and changed first menu item from "Create a Bill" to match other screens.
- **Episode 3 (Logo Overlap & Cart Redirect):** Shifted logo right by 3.5rem to resolve overlap; added conditional redirect when cart empties after deletion.
- **Episode 4 (Cart Accumulation & Navigation):** Implemented cart value accumulation when adding calculator values; added "Calculate" drawer redirect to dashboard; changed "Create a Bill" button to green "Pay Now."
- **Episode 5 (Prop Shadowing):** Identified local `const foodItems` shadowing parent prop; advised removing local constant and relying on parent-passed `foodItems`.
- **Episode 6 (Floating Cart Button):** Iteratively fixed cart button positioning—first tried inline `bottom: "5rem"` (failed), then aggressive positioning with `position: fixed`, `zIndex: 99999`, followed by centered implementation with `left: 50%`, `transform: translateX(-50%)`.
- **Episode 7 (OrderHistoryScreen):** Built from scratch using design specifications; resolved header-to-cards gap, card spacing (`gap-1` + `mt-1`), menu item ordering, and empty-state logic.
- **Episode 8 (UI Consistency):** Cross-referenced all screens to standardize header/menu/card layout; partially achieved consistency but noted remaining inconsistencies.
- **Episode 9 (Sheet/Drawer Trigger):** Moved `<Sheet>` outside the header flex container to match working pattern on other screens.
- **Episode 10 (Type Conflict Resolution):** Removed duplicate `Bill` type definition; used only imported `Bill` type; typed sample data as `Bill[]` to satisfy props.
- **Episode 11 (PaymentsListScreen):** Extracted UI patterns from existing screens; rewrote component to mirror previous five screens with consistent spacing, card structure, and navigation.

## 4. Debugging, Experiments, & Root Causes

**Root Cause 1: Prop Shadowing (Episode 5)**
- *Symptom:* Only one food item rendered despite a 15-item `foodItems` array.
- *Diagnosis:* Local `const foodItems: FoodItem[] = [...]` declared inside component shadowed the parent-provided `foodItems` prop due to lexical scoping.
- *Fix:* Remove local constant; rely exclusively on parent-passed prop; add debug logs to confirm prop flow.

**Root Cause 2: Floating Cart Button Positioning (Episode 6)**
- *Symptom:* Initial `bottom="5rem"` prop was invalid; inline CSS change removed error but didn't achieve desired position.
- *Experimentation:* Aggressive override with `position: fixed`, `zIndex: 99999`, `pointerEvents: "auto"`, transparent background, optional red border; then refined to centered implementation with `left: 50%`, `transform: translateX(-50%)`, `width: 100%`, `maxWidth: 480px`.
- *Verification:* User confirmed both aggressive and centered versions worked.

**Root Cause 3: TypeScript Type Conflicts (Episode 10)**
- *Symptom:* Duplicate `Bill` type re-declaration caused red-line errors, breaking drawer interaction in `OrderHistoryScreen7`.
- *Experimentation:* Removed local `Bill` type entirely; used only imported `Bill`; typed sample data as `Bill[]`; verified no TS errors after fix.

**Root Cause 4: Inconsistent Menu Ordering (Episode 8)**
- *Symptom:* Different screens had different first menu items (e.g., "Create a Bill" vs. "Calculate").
- *Resolution:* Standardized all screens to use "Create a Bill" as the first menu item.

## 7. Key Dependencies & Trade-offs

- **Dependency:** All screens depend on a shared `Bill` type exported from `App.tsx`. Any change to this type propagates to all screens.
- **Trade-off:** Using sample data (`sampleBills` constant) for demo purposes simplifies development but prevents real-world data integration. The `bills` prop allows switching to real data later.
- **Constraint:** The application uses a single-page architecture with no global drawer at `App` level; each screen manages its own `Sheet` component with fixed positioning.
- **Design Decision:** "Create a Bill" must be the first menu item across all screens for consistency, even though some screens originally had different orderings.

## 8. Summary

This evidence collection documents a multi-episode effort to build a coherent TASL Canteen React application. The project progressed from establishing a baseline (Episode 1) through iterative alignment (Episode 2-4), bug fixing (prop shadowing, floating cart positioning, type conflicts), and final screen implementation (OrderHistoryScreen, PaymentsListScreen6). While most screens are now consistent and functional, the codebase lacks full runtime validation, persistent data storage, and comprehensive accessibility/performance testing. The strongest signals are in technical correctness (correct prop handling, stable positioning, type safety) and product consistency (unified UI across screens). Remaining gaps include end-to-end workflow validation and production-readiness concerns (state-only bill persistence, lack of mobile responsiveness testing).
