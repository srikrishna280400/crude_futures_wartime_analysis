# Evidence Extraction — Office Canteen Order & Bill Management System

**Source scope note:** Single conversation summary; this is an intermediate extraction, not a final synthesis. Evidence is drawn only from this source and should not be synthesized across other conversations.

## 1. Problem, Goal, and Ambiguity

- **Goal (stated):** Build an internal tool to manage office canteen orders and bills — tracking employees/users, orders/bills, payments received, and outstanding balances.
- **Framing:** Problem described as clear but open-ended; genuine 0→1 challenge attributed to complete absence of a predetermined tech stack.
- **Key ambiguities raised:**
  - Whether to build custom code (Flask/SQLAlchemy) or adopt a no-code platform.
  - How to model relational data (users → orders → payments → outstanding) in a tool like Airtable.
  - How to authenticate against the Airtable API now that API keys were deprecated in favor of Personal Access Tokens (PATs).
  - How to fetch only needed fields, handle pagination, and filter records by the currently logged-in user.
  - Which frontend tool would pair best with Airtable (Thunkable, Bravo Studio, FlutterFlow, Glide, Bubble, Retool, AppGyver, Adalo, Framer).
  - Mobile/PWA deployment options within a free-tier budget.

## 2. User Actions (as attributed in source; assistant suggestions not separately itemized)

- **Flask prototype (Dec 12):** Built working Flask backend (`app.py`) with SQLAlchemy models — `User(id, name, contact_info)` and `Order(id, user_id, amount, status)` — backed by SQLite (`orders.db`). REST endpoints covered CRUD: `POST /users`, `POST /orders`, `GET /users/<id>/orders`, `PATCH /orders/<id>/pay`. Flow verified end-to-end via Postman and curl.
- **Airtable base design (from Dec 19):** Base named "Office Canteen Order and Bill Management" with four tables:
  - `Customers` (Employee ID, Name)
  - `Orders` (linked to Customer, amount, status)
  - `Payments` (linked to Customer, amount, date)
  - `Outstanding Amount` (rollup/summary)
  
  Linked records established relationships; rollups and formulas computed balances. Airtable Interface Designer screens built — calculator-like view with customer dropdown, amount input, "Add Bill" button, balance display.
- **Frontend platform evaluation:** User tested multiple platforms against criteria (screen limits, PWA support, Figma import, API integration ease, publishing cost, learning curve).
  - Retool: abandoned due to drag-and-drop friction.
  - Thunkable: free publishing, Web API component for Airtable; hit limitations duplicating buttons for calculator grid, configuring drawer navigator, handling multi-select components.
  - Bravo Studio: direct Figma import, free tester (Bravo Vision); publishing required paid plan.
  - FlutterFlow: Figma asset export (PNG/SVG), free tier, PWA publishing, multiple backend options (Firebase, Supabase, Airtable); Figma-to-Flutter plugin noted as alternative.
  - Glide, Bubble, AppGyver, Adalo, Framer assessed as fallbacks; AppGyver noted as "truly unlimited free" but steep learning curve.

## 3. Decisions and Trade-Offs (user-made per source)

- **Airtable as primary backend over Flask/MySQL** — rationale: faster MVP; built-in UI via Interface Designer; no hosting/database maintenance; relational features (linked records, rollups) sufficient for internal tool; accepted scalability ceiling.
- **Personal Access Tokens over deprecated API keys** — security/future-proofing; selected minimal scopes (least privilege): `data.records:read`, `data.records:write`, `schema.bases:read`.
- **Field IDs (`fld...`) over field names** in API requests — field names can change; IDs are immutable, preventing silent breakage.
- **`filterByFormula` for user-scoped data** — server-side filtering reduces payload and client-side logic; pattern `{fldIYmxrGYcyDTezd}="emp123"` used for payment history.
- **Pagination via `offset` + `maxRecords=100`** — Airtable enforces 100-record hard limit per request; iterative fetch loop required.

Frontend decisions: Thunkable initially chosen for mobile frontend; later limited by multi-select/button-duplication friction; Bravo Studio abandoned when publishing proved paid-only; FlutterFlow kept as alternative; Glide/AppGyver/Bubble kept as fallbacks.

## 4. Technical Evidence

- **Data model (as decided):**
  - `Customers` (Employee ID `fldkLwpg2c1Y7zj6M`, Employee Name `fld5wVhJydCuycgZn`) → `Orders` (linked to Customer, amount, status) → `Payments` (linked to Customer via `fldIYmxrGYcyDTezd`, Payment Amount `fldFwFPoP4kHM8Umi`, Payment Date `fld4Omrlr0Qq2p6M`) → `Outstanding Amount` (rollup/formula summary).
- **Canonical API request pattern:**
  ```
  GET /v0/{baseId}/{tableId}?fields[]=fldX&fields[]=fldY&filterByFormula=...&maxRecords=100&offset=...
  Authorization: Bearer pat...
  ```
- **Verified reusable API patterns:**
  - Employee list: `GET /v0/applNfL1uzUK6w1P1/Customers?fields[]=fldkLwpg2c1Y7zj6M&fields[]=fld5wVhJydCuycgZn`
  - Payment history for user: `GET /v0/applNfL1uzUK6w1P1/tble7CRyEW25W8bWM?fields[]=fldFwFPoP4kHM8Umi&fields[]=fld4Omrlr0Qq2p6M&filterByFormula=({fldIYmxrGYcyDTezd}="emp123")`
  - Outstanding amount detail: `GET /v0/applNfL1uzUK6w1P1/tbl4a3vsWLpMvzIN4/{recordId}`
- **Debugging episodes (user-driven, error → hypothesis → resolution):**
  - **401 Unauthorized:** Initial requests failed; user generated PAT in Airtable Developer Hub, added `Authorization: Bearer pat...` header, verified token worked in Postman.
  - **`INVALID_PERMISSIONS_OR_MODEL_NOT_FOUND`:** Switching from table name (`Payments`) to table ID (`tble7CRyEW25W8bWM`) resolved error; user confirmed PAT scopes included `data.records:read` for the specific base.
  - **Single record returned:** Recognized Airtable default page limit; added `maxRecords=100`; implemented `offset` loop to fetch all pages.
  - **Field selection:** Early requests returned all fields (payload bloat); adopted `fields[]=fldX` (URL-encoded as `fields%5B%5D=fldX`) to request only Payment Amount and Payment Date.
  - **User-scoped filtering:** Constructed `filterByFormula=({fldIYmxrGYcyDTezd}="emp123")`.
