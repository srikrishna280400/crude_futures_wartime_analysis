### Problem
- Desired a full‑stack employee bill system with role‑based login, manual bill entry, side navigation to Orders/Payments/Pending/Last Paid, and real‑time data sync.
- Ambiguity around which backend (Firebase vs. MySQL) and hosting approach would meet real‑time needs.
- Need to validate both employee code and scanned ID card against a secure data store.
- Required a mobile‑friendly UI with navigation and dynamic data retrieval per user.

### Approach
- **Phase 1 – Thunkable + Firebase**: Designed first‑screen UI, added Cloud Variable “employees”, built validation blocks (code check → scanner → navigate). Explored Firebase Realtime DB structure (`employees/{EMP001}/{name,id,...}`).
- **Phase 2 – MySQL Pivot**: Recognized MySQL could serve real‑time updates via API/WebSocket, decided to host MySQL online. Exported local DB, chose a cloud provider (AWS RDS/DigitalOcean), imported schema, configured remote access.
- **Phase 3 – Local Dev Stack**: Installed XAMPP, attempted phpMyAdmin access. Encountered Apache shutdown due to port conflict; changed Apache listen port to 8080, edited `httpd‑xampp.conf` to grant access, restarted services.
- **Phase 4 – No‑Code Platform Evaluation**: Compared Thunkable (native APK, 10‑screen free limit), Adalo (PWA only free), Kodular (Android‑only, no screen limit), Bravo Studio (Figma‑to‑app, free plan no screen limit), Bubble (web‑only, requires wrapper). Documented trade‑offs (branding, publishing constraints, native features).
- **Phase 5 – Design‑to‑Code Workflow**: Prepared Figma frames with Bravo tags (`#NavBar`, `#Button`, `#Input`). Installed Bravo Studio plugin, imported screens, linked API collections (Airtable/Firebase) for CRUD, previewed with Bravo Vision mobile app.

### Decisions
- **Backend Choice**: Started with Firebase for rapid Thunkable integration; later pivoted to MySQL for relational flexibility and control over real‑time updates via custom API.
- **Hosting**: Chose a managed MySQL service (AWS RDS/DigitalOcean) over self‑hosted VPS to simplify maintenance and scaling.
- **Local Development**: Adopted XAMPP as the unified Apache/MySQL/phpMyAdmin stack for offline work and quick testing.
- **App Platform**: Selected Thunkable for a quick native Android prototype (despite screen limit) to validate UI/UX before committing to a full‑scale solution.
- **Design‑to‑Code Pipeline**: Opted for Bravo Studio to convert Figma designs into functional mobile apps, leveraging its built‑in API connectors and Bravo Vision testing.
- **Free‑Tier Strategy**: Accepted Adalo’s PWA limitation for early prototyping, while reserving Thunkable/Kodular for downloadable APKs when needed.

### Build / Iteration
- **Thunkable Login Flow**: Added Text Input for employee code, Scanner component for ID card, Cloud Variable “employees”, validation blocks, navigation to Screen2 on success.
- **MySQL Hosting Steps**: Exported local `.sql` via phpMyAdmin, created online MySQL instance, imported schema, granted remote user privileges, tested connection via MySQL Workbench.
- **XAMPP Debugging**: Identified port‑80 conflict, edited `httpd.conf` (`Listen 8080`), modified `httpd‑xampp.conf` (`Require all granted`), restarted Apache, verified phpMyAdmin at `http://localhost:8080/phpmyadmin`.
- **No‑Code Platform Comparison**: Created a decision matrix (screen limits, native vs. PWA, branding, publishing constraints) and documented each platform’s free‑plan capabilities.
- **Bravo Studio Integration**: Installed Figma plugin, imported frames, added Bravo tags, linked API collections (e.g., Airtable “Employees” table), configured navigation between screens, previewed via Bravo Vision.

### Outcome
- **Technical Knowledge Gained**: 
  - End‑to‑end Thunkable login/authentication with Firebase Cloud Variable.
  - Hosting a MySQL database online, configuring remote access, and using API/WebSocket for real‑time updates.
  - Troubleshooting XAMPP Apache shutdown and phpMyAdmin 403 errors.
  - Evaluating no‑code platforms for native vs. PWA delivery, understanding screen limits and free‑plan constraints.
  - Converting a Figma design into a functional mobile app using Bravo Studio’s design‑to‑code pipeline.
- **Decision Framework**: A reusable matrix for selecting backend (Firebase vs. MySQL), hosting provider, and app builder based on requirements (real‑time sync, native features, screen count, branding).
- **Unresolved Questions**: 
  - Exact workflow for publishing a Bubble‑based web app as a native APK using third‑party wrappers (Nativator, Thunkable WebView) – no concrete steps were provided.
  - Whether Airtable can serve as a direct publishing platform for a full app (the assistant clarified it can only be a backend).
  - Detailed configuration for real‑time MySQL updates (WebSocket implementation) – only high‑level concepts were discussed.
- **Limitations**: No functional app was shipped; all work remained at design/prototype stage. Many “how‑to” queries were answered with guidance rather than executed implementations.
