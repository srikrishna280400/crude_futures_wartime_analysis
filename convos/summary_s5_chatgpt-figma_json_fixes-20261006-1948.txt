## Combined Summary: From Figma Design to Production PWA with Supabase Backend

This conversation documents the end-to-end development of a full-stack application that transforms Figma design files into a responsive Progressive Web App (PWA) with a backend for internal office order management. The user, working through a series of technical challenges, progressed from cleaning Figma JSON exports to designing and implementing a production-ready backend API, while navigating environment setup constraints and tooling trade-offs. The conversation captures the user's problem-solving approach, technical decision-making, and iterative development process across frontend, backend, and deployment domains.

---

### Problem

The user's primary goal was to build a working PWA that renders Figma designs as interactive, responsive React components, paired with a backend for an internal office order management system. The project spanned multiple technical domains, each with its own constraints and ambiguities.

On the frontend side, the user had a raw Figma JSON export that required extensive cleaning. The file—originally wrapped in a `.docx` file—contained structural issues including flattened layers that needed restoration, missing text styles, broken image references, incorrect constraint definitions, scroll behavior that was not properly encoded, invisible layers that should be removed, and inconsistent color formatting. The existing renderer used absolute positioning based on `absoluteBoundingBox` properties for every node, causing elements to overlap when the viewport resized. The JSON file was also too large (>25 MB) to paste directly into chat or online code editors, requiring a downloadable cleaned version. The user needed both a cleaned JSON file and a renderer that would produce responsive, mobile-ready layouts from the Figma source-of-truth.

On the backend side, the user initially envisioned a carbon-credit public application with users, journeys, CO₂ credits, and a wallet system. Through iterative scope refinement, the user clarified that the product is actually an internal office order-management tool—similar to a McDonald's kitchen display system but for employees. The refined requirements included employee login, menu management, order placement, staff status updates through a workflow (pending→preparing→ready→delivered), payment tracking across multiple methods (cash/UPI/card), and outstanding balance calculation per user. Public analytics and notifications were explicitly excluded from the MVP scope.

Additional constraints included the need for a fast development feedback loop, uncertainty about local development environment setup (the user was on Windows using VS Code and PowerShell, with limited C drive space), and a desire to keep the architecture flexible for future migration from Supabase to a MERN stack (MongoDB + Express + Node). The user also needed to understand the fundamental differences between JSON, JSX, and TSX file formats, the frontend versus backend engineering mindset, and the complete deployment pipeline from CodeSandbox prototype to production.

---

### Approach

The user tackled these challenges through iterative problem-solving, decomposition, and systematic tool evaluation.

**Frontend (Figma-to-React Pipeline).** The assistant generated a cleaned JSON file (`figma-fix.json`) with all 10 structural fixes applied, which the user could download. The user then shared their existing `renderer.jsx` file, which the assistant rewrote to map Figma's layout primitives to CSS flexbox. The key mappings included: `layoutMode` (HORIZONTAL/VERTICAL) → `flexDirection`, `layoutAlign`/`layoutGrow` → `alignSelf`/`flexGrow`, `__responsive.size` for width/height dimensions, and constraints for centering and scaling behavior. Text styles were extracted from the JSON and applied directly to the rendered elements. Images used `imageUrl` from the JSON rather than hardcoded placeholders.

When testing in CodeSandbox, the user encountered a series of errors that were systematically diagnosed and resolved. A `ModuleNotFoundError` for `./FigmaRenderer` and `./figma-fix.json` was traced to file placement—files needed to be in the `/src` directory with matching extensions (`.jsx`). A `ReferenceError: useMemo is not defined` was caused by a missing `import React, { useMemo, useEffect, useState } from "react"` statement. Slow loading times were explained by the recursive rendering of the entire JSON tree, which the assistant addressed by proposing a lighter renderer with a `screenIndex` prop to render one screen at a time. When the user asked about split JSON versus single JSON approaches, the assistant recommended Approach B (single JSON + `screenIndex`) for maintainability, faster screen switching, and easier updates when the data source eventually moves to a dynamic database.

**Backend (Office Order Management).** The user trimmed the scope through multiple iterations: from a full carbon-credit public app with wallets and journeys, to a comprehensive office system with staff roles and analytics, finally settling on a core architecture of five tables and 12 REST endpoints. The assistant designed a normalized PostgreSQL schema with `BIGSERIAL` primary keys for scalability, `created_at` timestamps for indexing, and monetary values stored as integer cents to prevent floating-point precision errors. A materialized view `user_balances` was created to aggregate total orders minus paid amounts per user, providing a clean, denormalized way to compute outstanding balances without recalculating on every request.

The API layer was built using Node.js + Express with parameterized queries (`$1`, `$2`, etc.) throughout to prevent SQL injection attacks. Transactional order creation was implemented using `BEGIN`/`COMMIT`/`ROLLBACK` with a PostgreSQL connection pool, ensuring that orders and their line items are inserted atomically—failures roll back cleanly to prevent partial states where an order exists without line items or vice versa. JWT-based route protection was added, verifying Supabase JWTs from the frontend while controlling which Express routes require a valid token. CORS middleware and JSON parsing were applied globally.

**Deployment & Architecture.** The assistant mapped the full path from CodeSandbox prototype to production: Vercel for frontend hosting (React PWA with manifest and service worker for installability), Supabase for the backend (PostgreSQL database, built-in authentication, and auto-generated REST API), and a clean API contract that would allow future backend migration to MERN without frontend changes. The assistant also explained the rationale behind JSON/JSX/TSX file formats—JSON as a universal data exchange format, JSX for UI composition inside JavaScript, and TSX as type-safe JSX—contrasting the frontend engineer mindset (display data, handle input, maintain UI consistency) with the backend mindset (data integrity, security, transactions).

**Testing Environment Selection.** When CodeSandbox proved too slow for iterative testing, the user evaluated alternatives. StackBlitz was recommended for its free, browser-based development environment using WebContainers, offering instant preview without local installation. Vite was offered as a local alternative for the fastest hot-reload experience, though this required installing Node.js. CodeSandbox Containers mode was rejected due to limited free quota that would hinder unlimited testing. The user initially requested a slow, step-by-step walkthrough for setting up Vite + React locally in VS Code, but when Node.js proved to be absent from the Windows machine, pivoted to StackBlitz as a lighter, browser-based alternative.

### Decisions

Several critical technical and product decisions shaped the project, each with clear rationale:

| Decision | Rationale |
|----------|-----------|
| **Single `figma-fix.json` + `screenIndex` prop** | Chosen over split JSON files for maintainability. A single source of truth simplifies design updates and scales naturally to dynamic data from a database later. The `screenIndex` prop allows rendering one screen at a time, improving performance and enabling state-driven screen switching. |
| **Flex/grid renderer using `layoutMode`, `constraints`, `__responsive`** | Rather than continuing with absolute positioning that caused overlapping on resize, the renderer was rewritten to interpret Figma's layout intent. Mapping Figma's auto-layout system to CSS flexbox makes the output responsive across devices without manual CSS adjustments, and constraints handle centering, scaling, and alignment. |
| **Fetch `figma-fix.json` from `/public` instead of import** | Large JSON files cause bundler issues in CodeSandbox and Vite when imported as modules. Fetching from the public folder avoids bundle inclusion and works for any file size. The trade-off is an asynchronous fetch with loading state rather than synchronous import. |
| **Supabase (PostgreSQL) over MERN (MongoDB + Express)** | The relational model fits the domain's transactional nature (orders, payments, balances) with ACID guarantees critical for money. Supabase provides managed PostgreSQL with built-in authentication and auto-generated REST APIs, significantly reducing time-to-production compared to building a custom Node/Express + MongoDB backend. |
| **Vercel for frontend hosting** | Zero-config deployment, free tier, GitHub integration, and edge network performance make it ideal for React PWAs. The platform handles PWA-specific requirements like service workers and manifests. |
| **API contract stability for future migration** | By keeping request/response shapes consistent across the fetch calls in the frontend, the backend can be swapped from Supabase to a custom MERN implementation without any changes to the React code. |
| **Integer cents for monetary values** | Storing money as integers (cents) rather than floats or decimals eliminates rounding errors that are common with floating-point arithmetic. Simple arithmetic works correctly at the cent level, and the conversion to dollars is handled only at the presentation layer. |
| **Transactional order creation** | Wrapping order and order_item inserts in a single PostgreSQL transaction prevents partial states. If any step fails (e.g., invalid `menu_item_id`, empty items array), the entire transaction rolls back. |
| **Plain JavaScript (JSX) over TypeScript for initial prototyping** | Reduced initial complexity and friction, allowing faster iteration on the renderer. TypeScript was considered for the production version but omitted from the initial setup to prioritize speed. |
| **StackBlitz over local Vite for immediate testing** | When Node.js was unavailable on the user's Windows machine, StackBlitz provided a zero-setup, browser-based alternative that eliminated the need to troubleshoot PATH configuration, drive space allocation, and local installation. |

### Build / Iteration

**Frontend Renderer Evolution.** The frontend renderer evolved through four distinct versions during the conversation:

1. **Original (user's):** Used `position: absolute` with `absoluteBoundingBox` for every node, hardcoded image placeholders, and no text styles. This caused overlapping elements on resize and did not encode any layout intent.

2. **Assistant v1:** Introduced flex layout from `layoutMode`, dimensions from `__responsive.size`, text styles applied from JSON properties, and image URLs extracted from the JSON. This was the first responsive version but still needed debugging.

3. **User's CodeSandbox iterations:** The user tested this version and encountered multiple errors. `ModuleNotFoundError` for `./FigmaRenderer` and `./figma-fix.json` was resolved by placing files in `/src` with matching `.jsx` extensions. `ReferenceError: useMemo is not defined` was fixed by adding the proper React hooks import. The `figma-fix.json not found` error was resolved by moving the file to the `/src` directory or using a fetch from `/public`.

4. **Assistant v2 (final):** Added proper React hook imports (`useState`, `useEffect`, `useMemo`), implemented `useEffect` to fetch `figma-fix.json` from `/public/figma-fix.json`, introduced a `screenIndex` prop for multi-screen switching, mapped constraints to CSS (`margin: 0 auto` for centering, `flex: 1` for scaling), converted scroll behavior to `overflow: auto`, added text fallbacks for nodes without characters, and wrapped the recursive `renderNode` function in `useMemo` for performance. This version handles TEXT, IMAGE, and container node types with proper style mapping.

**Backend Progression.** The backend progressed from concept to runnable, deployable code:

- **Schema design:** Five tables (`users`, `menu_items`, `orders`, `order_items`, `payments`) with foreign key relationships, indexes on `created_at` for query performance, and a materialized view `user_balances` that computes outstanding amounts automatically. The DDL was written as `schema.sql` and tested in the Supabase SQL editor.

- **Backend scaffolding:** Created `package.json` with dependencies (express, pg, cors, jsonwebtoken, bcrypt) and dev dependencies (nodemon). Set up `.env.example` with placeholders for `DATABASE_URL`, `PORT`, and `JWT_SECRET`.

- **Database connection:** Built `db.js` using the `pg.Pool` pattern, reading the connection string from environment variables to abstract away connection management.

- **Core endpoints:** Implemented each endpoint method-by-method with proper error handling. Menu CRUD operations include read/write with validation. Order creation uses transactional safety (BEGIN → INSERT order → INSERT order_items → COMMIT). Payment recording includes balance view lookup. Balance query endpoint uses the materialized view for fast reads.

- **Error handling:** Every async operation wraps results in try/catch blocks, logging errors to console and returning appropriate HTTP status codes (500 for server errors, 400 for bad requests with specific messages).

- **Validation checks:** The `/orders` endpoint validates that the `items` array is non-empty. The order creation transaction verifies that each `menu_item_id` exists and is available before inserting.

- **Documentation:** Inline comments explain each section, and a "Quick checklist to get this live now" section covers schema import, repo setup, deployment, and frontend integration.

**Testing Environment Setup Guide.** The setup guide provided step-by-step instructions for three environments, with a phased decomposition into six sequential phases: prerequisite check (Node/npm), local Vite scaffold, file creation with exact paths and content, dev server lifecycle, online sandbox replication, and troubleshooting. Two `FigmaRenderer.jsx` variants were provided: an import-based version for small JSON files and a fetch-based version for large JSON files that might cause bundler issues. A troubleshooting matrix was created covering five error classes: import path issues, JSON size limitations, missing hook imports, TypeScript friction, and sandbox-specific limits.
